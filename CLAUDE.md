## Architecture

**TigerTest** is a DMV practice test app built with Next.js 15 (App Router), React 19, TypeScript, and Firebase.

### Stack
- **UI:** Tailwind CSS + shadcn/ui (Radix primitives) in `/components/ui/`
- **State:** Zustand store (`/store/useStore.ts`) with localStorage persistence + Firebase Firestore sync
- **Auth:** Firebase Authentication (email/password + Google OAuth) via `/contexts/AuthContext.tsx`
- **Backend:** Firebase Firestore for user data, Resend for transactional email
- **Path alias:** `@/*` maps to project root

### Key Data Flow

All question data lives in `/data/questions.json` (~2,200 questions covering 50 states + DC). Questions are either `Universal` (shared across states) or `State-Specific`.

**Test generation** (`/lib/testGenerator.ts`) is deterministic — each of 4 tests gets a fixed slice of questions:
- Test N gets universal questions `[(N-1)*40 .. N*40-1]` + state-specific `[(N-1)*10 .. N*10-1]`
- 50 questions per test, 200 total per state
- Answer options are shuffled per attempt (skipped for position-dependent answers like "A and B")

**Training sets** mirror tests: 4 sets of 50 questions with mastery-based progression and a wrong-answer queue for spaced repetition.

### Zustand Store Structure

The store in `/store/useStore.ts` is the single source of truth. Key sections:
- `selectedState` — drives which questions are loaded; clearing state clears all progress
- `currentTests` — in-progress test sessions (questions, answers, timestamps)
- `completedTests` — full history of finished tests
- `training` / `trainingSets` — training mode progress with mastery tracking
- Firebase sync: `loadUserData()`, `saveToFirestore()`, `convertGuestToUser()`
- Data versioning (`DATA_VERSION = 2`) with migration logic on load

### Routing

App Router pages in `/app/`. Key routes:
- `/` — TigerTest hub homepage: "Popular this week" (six tests ranked by questions answered in the last 7 days from `analytics/questions.byExam`, `lib/server/popularTests.ts`, revalidated hourly), a DMV state grid, how it works with real app screenshots, the full catalog and a TigerTest FAQ. Catalog cards show a flag per language from `TestCatalogEntry.languages` (the DMV's es/vi/ko/zh, a v1 exam's `translations`)
- `/dmv-practice-test` — the DMV landing (the homepage until Oct 2026; same copy, own canonical; the catalog's DMV `href`)
- `/dmv/dashboard` — main hub (4 tests + 4 training sets), open to guests; the state picker is a card at the top until a state is chosen (`components/dashboard/DmvStatePicker.tsx`), then one line in the hero with Change (which asks first, since switching deletes progress). State landings link here with `?state=XX`, taken only while no state is set. `/dashboard` and the old `/onboarding/select-state` redirect here (`next.config.ts`); signup no longer asks for a state
- `/test/[id]` — practice test (1-4)
- `/test/[id]/results` — test results with performance breakdown
- `/practice/[n]` — mastery-based training set n (1-4); `/training` with no set is free practice
- `/stats` — per-question performance analytics
- `/admin` — admin dashboard (restricted by email in `/lib/admin.ts`)

Guest mode allows using the app without an account; guest data converts on signup.

**DMV languages.** The DMV flow runs in English, Spanish (every state), Vietnamese (`data/viStates.ts`), Korean (`data/koStates.ts`) and Simplified Chinese (`zh`, `data/zhStates.ts`: CA, NY, NJ, MA, WA, PA, MD, VA, the states whose DMV offers the knowledge test in Chinese; Texas offers only English and Spanish and Illinois publishes no language list, so both were left out in Oct 2026, and neither Texas nor Florida, English-only since Feb 2026, offers Vietnamese). The es, vi and ko banks mirror all 2,200 rows; the zh bank holds only the 160 universal questions plus the state-specific rows for its states and for TX and IL (translated before those were checked), and `getQuestionsZh()` in `lib/testGenerator.ts` fills every other row with English. The zh copy is machine-translated pending native review. The shuffle guard in `lib/shuffleOptions.ts` needs each language's "A and B" / "all of the above" wording; add it with a new language. The OG score card stays English for ko and zh (Inter has no CJK glyphs).

**Super Amazing Mode** (site-wide continuous fireworks, `components/SuperAmazingFireworks.tsx` in the root layout, flag `superAmazingMode` in localStorage) is earned by turning any dashboard all green: DMV 8/8, a registry exam's sets plus tests, or every v2 step (Premium-locked steps included, so SAT and ACT need Premium). `components/SuperAmazingCard.tsx` sits at the bottom of all three dashboards and owns the unlock: each dashboard's switch works only once that dashboard has been all green (`superAmazingUnlocks[key]`, key `dmv`, the registry exam id or `v2:<examId>`, never cleared by later progress; the fireworks stay site-wide once on). `superAmazingUnlockedAt` is only the first unlock anywhere, for the email and /admin, and never unlocks a switch (it was found on accounts that never went green). **Instructor classes** (`lib/classes.ts`, free): a signed-in teacher makes a class for any test on the site at `/teach/new` (a searchable picker over `TEST_GROUPS`: the DMV with a required state, stored as examId `dmv` plus the class's `state`; a v1 registry exam or its state version; or a v2 exam, by its own id; `classExamInfo()` resolves name, home, pass mark and topic labels for all three) and posts its link, `tigertest.io/c/<code>` (5 characters, no 0/O/1/I/L). Firestore: `classes/{code}` (teacherUid, examId, memberCount) and `classes/{code}/members/{memberId}` (answered, correct, byCategory, missed and seen per question, tests by number with best and attempts). The teacher's `/teach/classes/[code]` reads `/api/classes/[code]/report` (owner or site admin, `lib/server/classAuth.ts`), built by `lib/server/classReport.ts`: totals, topics weakest first, every question the class answered as the /stats `QuizRow` (most missed or lowest accuracy, tap for the options with the right answer marked, the class counts and the explanation; `components/teach/ClassQuestions.tsx`), and one row per student. A DMV class sets a new student's state on join; a student already on another state chooses to switch (resetting DMV progress, as Settings warns) or keep theirs. Question text for the class page comes from `lib/server/classQuestions.ts`, which loads the DMV, v1 and v2 banks. `/teach` is the indexed instructor landing (`components/teach/TeachLanding.tsx`, live mockups in `TeachPreviews.tsx`) and the class list once a teacher has classes. Not yet: Basics questions, the v1 drill page, progress from a second device, and teacher email digests.

The visitor funnel on `/admin/v2` (`lib/funnel.ts`, `/api/analytics/funnel`) counts signed-out browsers once per step: first visit, first question answered, signup page opened, account created. Counts go to `analytics/funnel`; each new account's origin (`tried` first or `cold`, plus its first visit's `source` and `landing` path, kept in localStorage from the visit step) goes to `signupOrigins/{uid}`, kept out of `users/{uid}` so it never races the first load.

`/admin/opportunities` (`lib/server/opportunities.ts`, `/api/admin/opportunities`, view in `components/admin/OpportunitiesView.tsx`) is the what-to-do-next page: every exam's practice, paywall views, purchases and revenue (what free exams would earn at the DMV's revenue per answer feeds the free-exam note only, not a column), paywalls with purchases per 100 views, visitors and signups by source, weekly retention cohorts, a data-health list and generated insights. It reads three Stripe listings read-only (completed checkouts for older payments' `location`, refunds, the webhook's events). The Stripe webhook now stores `location` and `exam` on each `payments` doc (`lib/purchaseAttribution.ts`; the DMV dashboard sends `training_set_4` / `practice_test_4` for the third set and test too) and marks `charge.refunded` as `refunded` / `partially_refunded` with `refundedCents`, never revoking Premium. At the top is a daily update written by Claude (`lib/server/dailyBrief.ts`, `claude-opus-5-5`): the cron `/api/cron/daily-brief` (weekdays 10:00 UTC, so by 7am Eastern in summer) sends the page's numbers plus the previous update's to the API and saves a headline and 3 to 5 bullets to `dailyBriefs/{Eastern date}`; "Write a fresh one" on the page calls `/api/admin/daily-brief`. **School referrals** (`lib/schoolReferral.ts`, `lib/schoolHosts.ts`, `/api/analytics/school-referral`): a visit whose referrer is a school LMS (Canvas, Blackboard, Brightspace, Moodle, Schoology, Google Classroom, Sakai) or a .edu / k12 site is reported once per browser per school and course, signed in or not (internal browsers skipped). Each host is a doc in `schoolReferrals` (visits, daily, landings with '/' stored as '|', and `courses` keyed by the course id read from the referrer path). The first visit from a new host, or a new course at a known host, emails John (`CAMPAIGN_REPLY_TO`, transactional, capped at 20 a day in `analytics/schoolReferralAlerts`): each is a teacher who posted a TigerTest link.

The "Questions by exam" table's Enrolled column counts distinct people with at least one answer per exam: one doc per (exam, person) in `enrollments` (`lib/enrollment.ts`, `/api/analytics/enrollment`), keyed `{exam}__u_{uid}` or `{exam}__b_{browserId}` for guests; signing in claims the browser's guest docs so a converted guest counts once. Accounts that predate it are seeded by `/api/admin/backfill-questions` (`enrollmentsBackfilledAt`).

`/api/admin/backfill-questions` is resumable: each call scans users for about 35s, saves its cursor and running sums in `analytics/questionsBackfillRun` (with a lease so two tabs never scan twice) and returns `done: false`; the admin pages loop through `lib/questionsBackfillClient.ts` until `done: true`. The anonymous answer counter (`/api/analytics/questions`) is capped per IP at 2,000 answers an hour and 6,000 a day (`lib/server/answerRateLimit.ts`, hashed IPs in `analyticsRateLimits`, TTL field `expiresAt`); dropped answers are tallied in `analytics/questions.rateLimited`.

**Internal accounts never count in /admin.** `lib/internal.ts` (`isInternalEmail`: `ADMIN_EMAILS`, `@johnbrophy.net`, `@stensul.com`) is applied on read by `/api/admin/metrics`, `/api/admin/users` and `/api/admin/backfill-questions` (uids from one cached Auth listing in `lib/server/internalUsers.ts`: users, payments, test requests and signup origins are dropped), and on write: an internal login marks the browser (`tigertest-internal` in localStorage, set in `AuthContext`, never cleared), after which the anonymous counters (questions answered, funnel steps, paywall hits, shares) are not sent from it even signed out; the paywall and funnel-signup routes also drop a request whose token is internal. Counts recorded before the flag existed stay in the aggregates. The stats cron has its own, broader `isTest()`.

### Additional Exams (CDL, HTL, CST, CRCST)

Non-DMV exams reuse the DMV components and store, namespaced by ID range and a
pseudo state code so progress never collides with DMV data. All of them are driven by the registry in `lib/exams.ts` (`ExamConfig`: state code, ID bases, slug, landing path, blueprint, training sets, category labels, dashboard copy). Each exam's bank is its own module, `lib/banks/<examId>.ts` (English plus any translated banks), registered into `lib/examData.ts` by `registerExamBanks()` and imported for that side effect only by the exam's test, training and stats pages, so a page bundles its own exam's questions and no other's (and never the DMV banks: answer shuffling lives in `lib/shuffleOptions.ts`); `lib/banks/all.ts` loads every bank for scripts only; `lib/examTestGenerator.ts` builds blueprint-weighted deterministic tests (test N takes slice N of each category pool, sorted by question ID) and training sets (one or more categories per set). No training session runs much past 50 questions: a set over 60 (`TRAINING_PART_MAX`) shows on the dashboard as parts of about 50, each its own step (`?set=N&part=P`; without `part` the page opens the first unfinished one). A part is a contiguous run of the set in question-ID order, and its start IDs and sizes are generated into `lib/trainingParts.json` by `npx tsx scripts/build-training-parts.ts` (the dashboard does not bundle banks); progress stays stored per set id and parts only filter it, so server progress, admin and emails are unchanged and existing mastery fills part 1 first. The script cuts where the category changes whenever sizes allow (a single-category set is cut evenly), and every split set carries hand-written `partNames` (what each part actually covers, e.g. CDL "Night Driving", "Weather Driving", "Mountains & Railroad Crossings"; Spanish ones in the CDL translation), shown on the dashboard, the training page and its "Next:" button; without them a part falls back to "<set>, part 2 of 3", and the script warns when the count does not match. Re-read the stems and rename when a split changes. Re-run the script (`--check` reports staleness and any set `size` that does not match its bank) after changing a bank or a set's categories. Pages under `app/<slug>/` are thin wrappers around `components/exam/*` (dashboard, test, results, training, drill, stats) plus a static SEO landing (`app/<slug>/page.tsx`, or `landingPath` when it lives elsewhere). `lib/testCatalog.ts` lists every test (DMV + registry) for the `/tests` hub, header switcher and footer.

### v2 exams (SAT and the other sectioned, timed exams)

`lib/v2/`, `components/v2/`, `store/useV2Store.ts`, `data/v2/` and `app/sat/` are a second engine that shares nothing with the v1 flow above (no `useStore`, no `lib/exams.ts`, no `QuestionCard`). It exists for exams the v1 shape cannot express: sections and modules with a clock, free navigation with flagging, passages beside the question, KaTeX, figures, multi-select and numeric (student-produced) answers, adaptive module 2, scaled scores.
- **Question model** is `QuestionV2` in `lib/v2/types.ts`, documented with examples in `data/v2/SCHEMA.md`. Formats: `single`, `multi` (select all that apply, or `select: N` for "Choose two"), `numeric`, `order` (tap steps into sequence), `highlight` (`{{phrase}}` markers in the passage or stem become tappable), `matrix` (`rows` x `columns`, one choice per row), `cloze` (`[[n]]` dropdowns in the stem from `blanks`) and `bowtie` (three `groups`: 2 actions, 1 condition, 2 parameters). Every answer is still a `number[]` or a numeric string (matrix and cloze hold -1 in unanswered slots), so sync, merge and analytics are format-blind. `lib/v2/grading.ts` has `isAnswered` (anything entered), `isComplete` (every row, blank and step filled, `select` met: drills enable Check on it and linear sections require it before Next) and `isCorrect` (all or nothing; order, matrix and cloze compare in sequence, the rest as sets). The inputs live in `components/v2/FormatInputs.tsx` (tap only, no drag, phone first); highlight and cloze render through `RichText`'s `renderSlot`. A case-study item carries both `stimulusId` and its own `passage`, and `getStimulus` shows the update ("New information") above the case. Eliminator and A-F keyboard picks apply to single and multi only. Options go up to 6 (A-F).
- **Source-built banks.** NCLEX, EMT, Security+, A+ and AWS are generated by `tools/build_v2_bank.py <exam>` from per-domain source files in `tools/<exam>/` (plus `stimuli.json` for case studies): it assigns ids so each test interleaves its domains (`<PREFIX>-T1-001..`, `-T2-..`, `-D-..`; a case study stays one block, ordered by `caseStep`). Edit the sources, never the built JSON. `tools/v1_to_v2_sources.py` was the one-off split of the old v1 banks. Validate any v2 bank with `tools/validate_v2_bank.py <exam> '<plan>'`, which checks each format's shape. Banks are JSON arrays tagged by `section`, `test`, `module` and optional `variant` (`lower`/`upper` for adaptive module 2); the test builder in `lib/v2/session.ts` filters on those tags, so adding a test is content only. Rich text (`components/v2/RichText.tsx`) handles `$...$` KaTeX, bold, italic, `__underline__`, bullets and pipe tables. Figures are SVG files under `public/figures/<exam>/`.
- **Exam config** is `ExamV2Config` (`lib/v2/exams/sat.ts`, registered in `lib/v2/registry.ts`): sections, modules with time limits, calculator and reference sheet, a raw-to-scaled curve per section (`curve()` anchors, an estimate, not an official table), a composite, drills by domain, goal choices.
- **Two modes, two devices.** `ExamRunner` is the desktop simulation (full-screen, timed, review screen, break, keyboard shortcuts A-E and arrows, calculator and reference panels) and also works on phones with a fixed bottom bar. `DrillRunner` is the phone-first mastery drill (one tap checks, misses come back until mastered, same mechanics as v1 training sets). Both use `QuestionView` and go full-screen via `.v2-focus` so site chrome never competes with the question. An exam's `drillSize` (20 on SAT and ACT, unset elsewhere) trims each drill to that many exam-level questions, an even spread across its difficulty-sorted pool in `drillQuestions` (`lib/v2/training.ts`), so the dashboard count, overview copy and mastery all follow that one number (`size` on a `DrillDef` overrides it). The pools themselves stay larger (test 1 plus the drill-only `test: 0` items; held-out tests never appear).
- **Store** `useV2Store` persists to localStorage under `tigertest-v2` (sessions, results, drills, goals, `syncedUid`). `components/v2/V2Sync.tsx` (mounted by `V2Shell` on every v2 page) mirrors it to the `v2` field of `users/{uid}` via `lib/v2/sync.ts`, written with `updateDoc` so the field is replaced whole and v1 fields are untouched. On sign-in, guest data is merged into the account with the pure `mergeV2` in `lib/v2/merge.ts` (results and mastered questions are unions, the further-along in-progress test wins, account goals win); on sign-out or a different account the local copy is cleared.
- **Dashboard** (`DashboardV2`) follows the v1 exam dashboards: goal picker first, then a hero with the tiger face ladder and an N/9 step counter (one step per drill plus one per full test; a test step completes when its best score reaches the goal), on the shared `ProgressCard`. Drills draw every bank item in their domains except items from a test marked `heldOut` in the config (`heldOutTests()` in `lib/v2/training.ts`); items tagged `test: 0` are drill-only. SAT and ACT hold out Practice Test 2 so it measures readiness, not memory. `V2Header` replaces the DMV header on v2 paths (`getExamV2ByPath` in `lib/v2/registry.ts`), and the footer uses the compact exam footer.
- **SAT** (`/sat`, landing `/sat-practice-test`, catalog id `sat` in `lib/testCatalog.ts`, first in the "College, military & nursing school entrance" group, `[data-theme="sat"]` blue): two full practice tests, fully adaptive. Files in `data/v2/sat/`: Test 1 is `rw-m1`, `rw-m2` (variant upper), `rw-t1-m2-lower`, `ma-m1`, `ma-m2` (upper), `ma-t1-m2-lower`; Test 2 is `rw-t2-m1`, `rw-t2-m2-{lower,upper}`, `ma-t2-m1`, `ma-t2-m2-{lower,upper}`. Each R&W module is 27 items in 32 min, each Math module 22 in 35 min with 6 numeric items; module 2 variant is picked from module 1 accuracy (threshold 0.6). Drill-only items (`test: 0`) are `rw-drill-{a,b}` (SAT-RW-001..080) and `ma-drill-{a,b,c}` (SAT-MA-001..100; `c` tops up data analysis and geometry). 474 original items in all; Test 2 is held out of the drills. Validate with `tools/validate_v2_bank.py`.
- **ACT** (`/act`, landing `/act-practice-test`, `[data-theme="act"]` red): enhanced 2025 format, four choices everywhere. English 50 in 35 min (5 shared passages, `__underlined__ [N]` markers), Math 45 in 50 min with calculator and a break after, Reading 36 in 40 min (4 passages, one paired), Science 40 in 40 min (6 passages with pipe tables). Two full tests plus a drill-only bank, all in object form `{ stimuli, questions }` merged by `withStimuli()` in `lib/v2/banks/act.ts`: Test 1 is `{english,math,reading,science}-{a,b}.json` (ids 101.., stimuli P1-P6 per section), Test 2 is `*-t2{a,b}.json` (ids 201.., stimuli P6+/P5+/P7+) and is held out of the drills, and `drill-{english,math-a,math-b,reading,science}.json` are `test: 0` items (ids 001.., stimuli `D1`..) with shorter passages for the phone. Questions reference `stimulusId` and ids sort in passage order. Drills are the eleven ACT reporting categories (Reading's small Integration category shares a drill with Craft and Structure); each has `legacyKey` pointing at the section drill it replaced, so `drillStateFor()` in `lib/v2/training.ts` carries old progress forward until the new drill has its own. Each section is scaled 1 to 36 with `curve()`; the composite averages English, Math and Reading, and Science reports on its own. `ExamRunner` keys `QuestionView` by `stimulusId` so a shared passage keeps its scroll across its questions. `breakAfter` on a section limits the exam's break to that section change. The OG card at `/og/act` and the exams sitemap both know about it. ACT has its own eight-expression tiger set in `public/tigers/act/`, selected through `lib/tigerAssets.ts`.
- **Basics** (`lib/v2/basics.ts`, library split across `data/v2/basics/{skills,reading,math,science,writing}.json`, 83 skills) is the free first level inside a phone drill, for students the exam-level items are too hard for: one rule a drill depends on (semicolons, slope, reading a table) as a rule card (rule, "the trick", good/bad examples, an ELI5 explanation in kid words behind the "ELI5" button) plus 2 one-line questions (`blank` with `__`, or a `stem`, with an optional `table` or a 2 to 3 sentence `passage` for reading and science skills; punctuation options show their names; options are shuffled per question by `basicsOptionOrder`). Misses come back until right, two misses bring the rule card back once. Skills are one shared library; a drill lists the ids it opens with in `DrillDef.basics` (SAT and ACT Conventions share Semicolons). TEAS uses it too: its Math and English drills are split by ATI subdomain (Numbers and Algebra, Measurement and Data, Grammar and Punctuation, Language and Vocabulary, each with `legacyKey` to the old section drill) and open with the shared cards plus seven TEAS math walkthroughs (fractionConvert, fractionOps, orderOfOperations, percentChange, scientificNotation, dosage, volume); Science has no Basics yet. 78 of the 200 TEAS items carry a `basics` tag. HESI A2, ACCUPLACER and ASVAB use it too (their `train` pages are `TrainPage`): HESI Math is split into Numbers and Operations (`hesiNumbers`) and Conversions and Dosage (`hesiConversions`), ACCUPLACER Writing into Standard English Conventions (`accConventions`) and Expression of Ideas (`accExpression`), each with `legacyKey` to the old drill and the old domain kept in `domainLabels`; HESI reading, vocabulary and grammar, every ACCUPLACER drill, and ASVAB AR, WK, PC and MK open with Basics. Skills added for them: romanNumerals, militaryTime, decimals, rounding, negativeNumbers, gcfLcm, distributing, substitution, squareRoots, rateProblems, wordProblems, factOpinion, wordParts, synonyms (walkthroughs) and commonlyConfused, pronounCase, verbTense, listIntroCommas (voiced explainers, recorded through the ElevenLabs connector and built with `--align`). 394 of their 600 items carry a `basics` tag; the science and technical drills have no Basics. `/<slug>/train?drill=k` is `TrainPage`: the `DrillOverview` (skill list, then the exam level, which opens when every skill is learned or on "skip ahead") when the drill has Basics, `&skill=id` is `BasicsRunner`, `&level=exam` is the unchanged `DrillRunner`. Learned skills are `basics[`${examId}:${skillId}`]` in `useV2Store` (synced and merged like drills). On the dashboard each drill with Basics is two numbered steps, "<drill> [Basics]" (green when every skill is learned) then the drill itself, and both count in the N/N; the exam step always links straight to the questions, so anyone who already knows the basics just taps it (the overview has no skip link). A Premium drill gates both steps, Basics included (`isDrillLocked` + `hasDrillProgress` in `lib/v2/premium.ts`); the overview, `BasicsRunner` and `DrillRunner` all show the shared `DrillLockScreen`, and a drill someone already has progress in (exam-level or a learned skill) stays open.
- **Brush up from the exam level** (`lib/v2/skillMatch.ts`, `components/v2/BasicsRuleSheet.tsx`, `components/v2/BasicsRuleCard.tsx`): a missed `DrillRunner` question offers "Brush up on the basics · <skill>", which pops the same rule sheet a Basics question's Rule button opens (shared `BasicsRuleSheet`: "Listen instead" when voiced, the `RuleCard`, ELI5, "Back to the question"). The skill comes from the question's hand-set `basics` tag (`QuestionV2.basics`, a Basics skill id; 329 of the 376 drill-pool items carry one, the other 47 have no skill for their rule, e.g. dashes, parallel structure, verb tense, and get no card). `matchBasicsSkill(question, drill)` returns the tagged skill if the drill opens with it, else an exact `skill`-label match, else null; nothing fuzzier, because cue-word matching against explanations sent comma questions to Semicolons. Tag new drill-pool items when adding them; the untagged list is also the list of Basics skills worth writing next.
- **Two ways to learn a skill, by what the skill is.** A skill that is one sentence to recognise (the 12 grammar skills and the 4 single-sentence writing skills: redundancy, concision, preciseWords, matchingTone) gets the voiced **explainer** video below. Everything else, 53 skills, is a procedure or passage work (all math, all reading, all science, the paragraph-level writing skills, Transitions) and gets a click-through **walkthrough** instead: watching a procedure does not teach it, supplying each step does. `BasicsRunner` leads the learn screen with the walkthrough when the skill has one, else the explainer when voiced, else the text card; the text card is always behind "Read it", and the rule sheet (`BasicsRuleSheet`, from the Rule button and from a missed exam-level question) offers "Walk through it, step by step" and "Listen instead" as the skill has them.
- **Basics walkthrough** (`BasicsWalkthrough` in `lib/v2/basics.ts`, `components/v2/BasicsWalkthrough.tsx`, content in each skill's `walkthrough` field): a board pinned on top (`board` text, `kind: "math"` for a large centred expression, or `passage: true` / `table: true` for the skill's own) and 3 to 7 steps under it, each either `say` (read it, Next) or `ask` (two or three options; a wrong tap shows `hint` and stays tappable, the right one shows `then`). A step's `line` is added to a work column under the board when it is done, the last such line green, so the solution builds up from the student's own taps. No voice, no clock, no score; the review after two misses and the miss feedback button ("Walk through it again") reuse it. Authoring rule for math: say the mapping (which number is c), show the search (list the pairs), check the answer; for reading and science: the steps are the strategy itself (name the point, find the signal word, put a finger on the words). Option order is `basicsOptionOrder(skillId, 100 + step, n)`.
- **Basics explainer** (`lib/v2/explainer.ts`, `components/v2/BasicsExplainer.tsx`) is a 30-second animated walk through one skill: rule, trick, a sentence that breaks it, one that follows it, "now you try" (the ELI5 picture stays on the rule card behind its button). A voiced skill is video first: opening it shows the explainer's Play screen with "Read it" to the text card, the review after two misses does the same, a miss offers "Watch the explainer", and the rule sheet behind a question's Rule button opens on a "Listen instead" link (the overlay's "Read it" drops back into that sheet); the text card keeps a "Watch it instead" link. The Play tap is the gesture phones require before sound, so `play()` is called inside it and nothing guesses about autoplay. The storyboard is built from the skill's own fields, so there is one template per example style, not one video per skill (`explainerTemplate`, no table or passage either way): Sentence (a good/bad pair) strikes the words that differ in the bad sentence and marks them in the good one; Worked (math `eg` examples with a note) shows each expression large, then the note's sentences as numbered steps as they are spoken, the last ("So ...") green as the answer. Worked exists and Factoring is voiced with it, but math skills lead with their walkthrough; do not voice more math. The voice script goes through `speakable()` in the build script (x² is "x squared", · is "times", ")(" is ", times", a leading − is "negative"), and the aligner expands each written word the same way, so "x²" takes the span of both spoken words; the screen keeps the notation. ### SEO conventions

- **Landing pages** (`app/<x>-practice-test/page.tsx`) are the only exam URLs meant to rank. Each sets its own metadata (title, description, canonical, Open Graph image at `/og/<examId>` from `app/og/[examId]/route.tsx`) and a `WebApplication` + `FAQPage` JSON-LD graph (no breadcrumb: removed Oct 2026, the crumb pushed the headline down and Google no longer shows trails on mobile), and renders `<ExamRelatedTests examId>` before the final CTA (cross-links within the exam's hub group from `relatedTests()` in `lib/testCatalog.ts`). Write metadata and JSON-LD strings with plain apostrophes; `&apos;` only belongs in JSX text.
- **App routes** (`app/<slug>/layout.tsx`) export `examAppMetadata(id)` from `lib/examSeo.ts`: the exam's own title and `noindex, follow`. They are deliberately not disallowed in `app/robots.ts` so crawlers can read the tag. DMV app routes keep their robots.txt disallow.
- **GEO (AI answer engines)**: every exam landing renders `<ExamFacts examId>` under the hero: a plain answer about the real exam, a facts table and a dated "based on" line with the official source, plus a `WebPage` node with `dateModified` (`EXAM_LANDINGS_UPDATED_AT`). The facts live in `lib/examFacts.ts`; keep them in step with the landing's FAQ and add an entry with each new exam. `/llms.txt` and `/llms-full.txt` are generated from the catalog, exam facts and state data (`lib/llmsTxt.ts`, DMV first, with the 51-state written-test table). The site-wide `Organization` and `WebSite` nodes are in `lib/siteSchema.ts`, rendered once by `app/layout.tsx`; point new JSON-LD at them by `@id`. `app/robots.ts` gives every crawler, AI or not, the same allow/disallow lists. First visits are counted by source (`visitSource()` in `lib/funnel.ts`: ChatGPT, Perplexity, Gemini, Copilot, Claude, search, direct, other), shown on `/admin/v2`. DMV state pages are deliberately left as they are.
- **Footer** links stay inside the current test's cluster (`relatedTests`): DMV pages link to CDL, endorsements and motorcycle plus the `/tests` hub, never all thirty exams.
- **Sitemap** is an index (`app/sitemap.xml/route.ts`) over per-family files in `app/sitemaps/[segment]/route.ts` (`dmv`, `dmv-es-vi-ko` (which also holds the Chinese pages; the name is kept so Search Console keeps its history), `exams`; `/teach` is in `exams`) built by `lib/sitemaps.ts`, so Search Console shows DMV coverage separately. `lastmod` comes from the hand-bumped dates in `lib/seoDates.ts`; bump the relevant constant when a page family's content changes.

These pages are the DMV flow, not the CDL one: `lib/examRoutes.ts` (`DMV_ROUTES` / `getExamRoutes(id)`) parameterises the shared pieces (`hooks/useTestResults.ts`, `components/results/*`, `components/MissDrill.tsx`, `components/dashboard/ProgressCard.tsx`, `lib/missedQuestions.ts`, `components/AttemptChart.tsx`) by route base, test IDs, pass line, and premium gating. Defaults reproduce DMV behaviour exactly; when changing the DMV results/drill/dashboard flow, keep every exam working.

Theme colors come from the `[data-theme="<examId>"]` blocks in `app/globals.css`; `contexts/TestThemeContext.tsx` and `components/HeaderSwitch.tsx` pick the header by path. ### Dark mode

Class strategy (`darkMode: ["class"]`): `contexts/ThemeContext.tsx` keeps the preference (`light` / `dark` / `system`) in localStorage under `tigertest-theme` (a device setting, never synced to the account), toggles `dark` on `<html>` and follows the OS while on `system`. `THEME_INIT_SCRIPT` runs inline in `app/layout.tsx` `<head>` so a dark reader never sees a white flash; `<html>` carries `suppressHydrationWarning` for that reason. `components/ThemeToggle.tsx` is the picker in every header and the footer, and `ThemeSegmentedControl` the one on `/settings`; labels are under `theme.*` in `i18n/*`.

Components keep their light classes and carry a `dark:` companion, one palette throughout: page `bg-gray-50` becomes `dark:bg-gray-950`, cards `bg-white` become `dark:bg-gray-900`, insets `bg-gray-100` become `dark:bg-gray-800`, borders `gray-200` become `dark:gray-800`, body text `gray-900` becomes `dark:gray-50`, secondary `gray-600` becomes `dark:gray-300`; tinted boxes go to the deep end of their hue (`bg-green-50 dark:bg-green-950`, `text-green-700 dark:text-green-300`); black CTA buttons (`bg-black text-white`) invert to white; translucent whites and blacks, solid brand and semantic fills, and `text-gray-400` stay as they are; hero gradients end on `dark:to-transparent`. The shadcn tokens in the `.dark` block of `globals.css` use the same grays. `tools/add_dark_variants.py` applies those rules mechanically and is idempotent, so run it after adding a page or component that uses hardcoded palette classes (or write the `dark:` companion by hand). Per-theme brand tints for dark (`.dark [data-theme=...]`, brand-light, gradient-to, border-light darken; brand-dark and brand-darker lighten; brands under 50% lightness lift to 50%) are generated by `tools/gen_dark_brand_css.py`; re-run it when adding a theme block. v2 exams get the same tints at runtime from `lib/v2/darkTheme.ts` through `V2Shell`, and `components/v2/v2.css` carries the `.dark .v2-shell` / `.dark .v2-focus` overrides. v2 figures are grayscale SVGs and are shown with `dark:invert`.

### Email

Resend, from `noreply@tigertest.io`, reply-to John. Templates are HTML strings in `lib/email-templates.ts`, one function of an `EmailVoice` (`lib/email-voice.ts`) each. Daily campaign crons under `app/api/cron/*` (schedules in `vercel.json`) share `lib/cron-email.ts`: one Auth list call, `getEligibleUsers()` (consent, opt-out, quiet-days rule per exam), a 24h frequency cap, a once-only `emailsSent` key per campaign, and the account-wide daily budget in `lib/email-quota.ts` (bump `CAMPAIGN_CRON_COUNT` when adding a cron). `scripts/email-dryrun.mjs` shows who each cron would reach without sending.

Opt-out is `users/{uid}.unsubscribed` (`lib/unsubscribe.ts`). It is checked in the audience query and again in `sendCronEmail()` right before every send, and every campaign carries RFC 8058 `List-Unsubscribe` headers pointing at `/api/unsubscribe` (GET and one-click POST). Nothing on the client writes that field. The new-tests campaign (`newTests2026`) is paused unless `NEW_TESTS_CAMPAIGN=send`; while paused each daily run only logs how many people it would reach. DMV readers are split across the variants still sending in `lib/email-launch.ts` (v4 and v5; v1 and v3 retired Oct 17 via `RETIRED_VARIANTS` but still reported on `/admin/v2`) (one per user, stable by uid, stamped as `emailVariants.newTests2026` on send; links go through `/api/email/click`, which records `emailClicks.newTests2026`); `/admin/v2` compares sends, clicks and purchases per variant. Non-DMV readers get the short version, outside the test. It also asks "what should we build next?": clicks land in the `testRequests` collection via `/api/feedback/test-request` and `/request-test` (`lib/test-requests.ts`), shown on `/admin/v2`; a named exam emails John immediately.

### Mobile Apps

`/mobile/` contains a Capacitor 8 shell (app id `io.tigertest.app`) that loads
the production site in a native WebView for iOS and Android. The site detects
the shell via a `TigerTestApp` user-agent token (`lib/native-app.ts`,
`hooks/useIsNativeApp.ts`) and hides Google Sign-In and Stripe checkout
(store-policy compliance) and applies safe-area CSS. After changing
`mobile/capacitor.config.ts`, run `npx cap sync` in `/mobile` and commit the
result. Store submission guide: `docs/APP_STORE_DEPLOYMENT.md`.

### Agentic Question Rewrite System

`/agentic-rewrite/` contains a multi-agent pipeline for generating and validating questions. A supervisor agent orchestrates generators and four validator agents (distribution, memorization, format, answer-length) with a fixer agent for corrections. State question files live in `/agentic-rewrite/states/`.
