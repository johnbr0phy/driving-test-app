## Architecture

**Tigertest** (always written "Tigertest" in copy and the logo; never TigerTest or tigertest, except in URLs, keys and the `TigerTestApp` user-agent token) is a DMV practice test app built with Next.js 15 (App Router), React 19, TypeScript, and Firebase.

### Stack
- **UI:** Tailwind CSS + shadcn/ui (Radix primitives) in `/components/ui/`
- **State:** Zustand store (`/store/useStore.ts`) with localStorage persistence + Firebase Firestore sync
- **Auth:** Firebase Authentication (email/password + Google OAuth) via `/contexts/AuthContext.tsx`
- **Backend:** Firebase Firestore for user data, Resend for transactional email
- **Path alias:** `@/*` maps to project root

### Key Data Flow

All question data lives in `/data/questions.json` (~2,200 questions covering 50 states + DC). Questions are either `Universal` (shared across states) or `State-Specific`.

**Test generation** (`/lib/testGenerator.ts`) is deterministic — each of 4 tests gets a fixed slice of questions:
- Test N gets universal questions `[(N-1)*40 .. N*40-1]` + state-specific `[(N-1)*10 .. N*10-1]`
- 50 questions per test, 200 total per state
- Answer options are shuffled per attempt (skipped for position-dependent answers like "A and B")

**Training sets** mirror tests: 4 sets of 50 questions with mastery-based progression and a wrong-answer queue for spaced repetition.

### Zustand Store Structure

The store in `/store/useStore.ts` is the single source of truth. Key sections:
- `selectedState` — drives which questions are loaded; clearing state clears all progress
- `currentTests` — in-progress test sessions (questions, answers, timestamps)
- `completedTests` — full history of finished tests
- `training` / `trainingSets` — training mode progress with mastery tracking
- Firebase sync: `loadUserData()`, `saveToFirestore()`, `convertGuestToUser()`
- Data versioning (`DATA_VERSION = 2`) with migration logic on load

### Additional Exams (CDL, HTL, CST, CRCST)

Non-DMV exams reuse the DMV components and store, namespaced by ID range and a
pseudo state code so progress never collides with DMV data. All of them are driven by the registry in `lib/exams.ts` (`ExamConfig`: state code, ID bases, slug, landing path, blueprint, training sets, category labels, dashboard copy). Each exam's bank is its own module, `lib/banks/<examId>.ts` (English plus any translated banks), registered into `lib/examData.ts` by `registerExamBanks()` and imported for that side effect only by the exam's stats and drill pages and loaded on demand by the shared test and practice pages, so a page bundles its own exam's questions and no other's (and never the DMV banks: answer shuffling lives in `lib/shuffleOptions.ts`); `lib/banks/all.ts` loads every bank for scripts only; `lib/examTestGenerator.ts` builds blueprint-weighted deterministic tests (test N takes slice N of each category pool, sorted by question ID) and training sets (one or more categories per set, or a test's own questions; see DMV-style test sets below). No training session runs much past 50 questions: a set over 60 (`TRAINING_PART_MAX`) shows on the dashboard as parts of about 50, each its own step (`?set=N&part=P`; without `part` the page opens the first unfinished one). A part is a contiguous run of the set in question-ID order, and its start IDs and sizes are generated into `lib/trainingParts.json` by `npx tsx scripts/build-training-parts.ts` (the dashboard does not bundle banks); progress stays stored per set id and parts only filter it, so server progress, admin and emails are unchanged and existing mastery fills part 1 first. Re-read the stems and rename when a split changes. Re-run the script (`--check` reports staleness and any set `size` that does not match its bank) after changing a bank or a set's categories. Pages under `app/<slug>/` are thin wrappers around `components/exam/*` (dashboard, drill, stats) plus a static SEO landing; the test, results and practice pages of every v1 and v2 exam are one shared set of routes, `app/[slug]/test/[id]`, `app/[slug]/test/[id]/results` and `app/[slug]/practice/[n]` (`components/exam/SharedExamAppPage.tsx`, layout `SharedExamAppLayout.tsx`), which find the exam by its `slug` (`examForAppSlug()` in `lib/examAppRoute.ts`) and import its bank on demand (`loadExamBank()`, one chunk per bank, so a bank file must be named by the exam id). ### v2 exams (SAT and the other sectioned, timed exams)

`lib/v2/`, `components/v2/`, `store/useV2Store.ts`, `data/v2/` and `app/sat/` are a second engine that shares nothing with the v1 flow above (no `useStore`, no `lib/exams.ts`, no `QuestionCard`). It exists for exams the v1 shape cannot express: sections and modules with a clock, free navigation with flagging, passages beside the question, KaTeX, figures, multi-select and numeric (student-produced) answers, adaptive module 2, scaled scores.
- **Question model** is `QuestionV2` in `lib/v2/types.ts`, documented with examples in `data/v2/SCHEMA.md`. Formats: `single`, `multi` (select all that apply, or `select: N` for "Choose two"), `numeric`, `order` (tap steps into sequence), `highlight` (`{{phrase}}` markers in the passage or stem become tappable), `matrix` (`rows` x `columns`, one choice per row), `cloze` (`[[n]]` dropdowns in the stem from `blanks`) and `bowtie` (three `groups`: 2 actions, 1 condition, 2 parameters). Every answer is still a `number[]` or a numeric string (matrix and cloze hold -1 in unanswered slots), so sync, merge and analytics are format-blind. `lib/v2/grading.ts` has `isAnswered` (anything entered), `isComplete` (every row, blank and step filled, `select` met: drills enable Check on it and linear sections require it before Next) and `isCorrect` (all or nothing; order, matrix and cloze compare in sequence, the rest as sets). The inputs live in `components/v2/FormatInputs.tsx` (tap only, no drag, phone first); highlight and cloze render through `RichText`'s `renderSlot`. A case-study item carries both `stimulusId` and its own `passage`, and `getStimulus` shows the update ("New information") above the case. Eliminator and A-F keyboard picks apply to single and multi only. Options go up to 6 (A-F).
- **Source-built banks.** NCLEX, EMT, Security+, A+ and AWS are generated by `tools/build_v2_bank.py <exam>` from per-domain source files in `tools/<exam>/` (plus `stimuli.json` for case studies): it assigns ids so each test interleaves its domains (`<PREFIX>-T1-001..`, `-T2-..`, `-D-..`; a case study stays one block, ordered by `caseStep`). Edit the sources, never the built JSON. `tools/v1_to_v2_sources.py` was the one-off split of the old v1 banks. Validate any v2 bank with `tools/validate_v2_bank.py <exam> '<plan>'`, which checks each format's shape. Banks are JSON arrays tagged by `section`, `test`, `module` and optional `variant` (`lower`/`upper` for adaptive module 2); the test builder in `lib/v2/session.ts` filters on those tags, so adding a test is content only. Rich text (`components/v2/RichText.tsx`) handles `$...$` KaTeX, bold, italic, `__underline__`, bullets and pipe tables. Figures are SVG files under `public/figures/<exam>/`.
- **Exam config** is `ExamV2Config` (`lib/v2/exams/sat.ts`, registered in `lib/v2/registry.ts`): sections, modules with time limits, calculator and reference sheet, a raw-to-scaled curve per section (`curve()` anchors, an estimate, not an official table), a composite, drills by domain, goal choices.
- **Two modes, two devices.** `ExamRunner` is the desktop simulation (full-screen, timed, review screen, break, keyboard shortcuts A-E and arrows, calculator and reference panels) and also works on phones with a fixed bottom bar. `DrillRunner` is the phone-first mastery drill (one tap checks, misses come back until mastered, same mechanics as v1 training sets). Both use `QuestionView` and go full-screen via `.v2-focus` so site chrome never competes with the question. An exam's `drillSize` (20 on SAT and ACT, unset elsewhere) trims each drill to that many exam-level questions, an even spread across its difficulty-sorted pool in `drillQuestions` (`lib/v2/training.ts`), so the dashboard count, overview copy and mastery all follow that one number (`size` on a `DrillDef` overrides it). The pools themselves stay larger (test 1 plus the drill-only `test: 0` items; held-out tests never appear).
- **Store** `useV2Store` persists to localStorage under `tigertest-v2` (sessions, results, drills, goals, `syncedUid`). `components/v2/V2Sync.tsx` (mounted by `V2Shell` on every v2 page) mirrors it to the `v2` field of `users/{uid}` via `lib/v2/sync.ts`, written with `updateDoc` so the field is replaced whole and v1 fields are untouched. On sign-in, guest data is merged into the account with the pure `mergeV2` in `lib/v2/merge.ts` (results and mastered questions are unions, the further-along in-progress test wins, account goals win); on sign-out or a different account the local copy is cleared.
- **Dashboard** (`DashboardV2`) follows the v1 exam dashboards: goal picker first, then a hero with the tiger face ladder and an N/9 step counter (one step per drill plus one per full test; a test step completes when its best score reaches the goal), on the shared `ProgressCard`. Drills draw every bank item in their domains except items from a test marked `heldOut` in the config (`heldOutTests()` in `lib/v2/training.ts`); items tagged `test: 0` are drill-only. SAT and ACT hold out Practice Test 2 so it measures readiness, not memory. A "Your stats" card at the bottom links to `/<slug>/stats` (`StatsV2`, one wrapper per exam copied from its dashboard page). - **TEAS** alternate items: 30 of its 200 items are select all that apply (12), typed numeric (10) and ordered response (8), like the real TEAS 7's up to 15%; image hot spots are not modelled. Drill-only TEAS items are `module: 1`.
- **Premium** is the one DMV purchase (`$9.99` one-time, `users/{uid}.subscription.isPremium`), which also unlocks any v2 exam whose config sets `premium` (none since Oct 31, 2026, when the SAT and ACT went fully free; the gates below stay in place for a future one). Logic is in `lib/v2/premium.ts`; `useIsPremium()` reads the flag once auth settles. `V2TestGate` fronts every v2 test route (an in-progress or already-sat test stays open), `DrillRunner` shows a lock screen for a locked drill (open anyway if the person already has their own progress in it), and `DashboardV2` locks those steps and the test step and verifies the Stripe return (`usePurchaseReturn`; checkout takes a same-site `returnPath`). v2 paywall item ids start `v2_` so the DMV paywall-abandon email skips them. Client-side gating, like the DMV. The v1 registry exams of the US (`regionOfTest()` in `lib/region.ts`; other countries' exams keep their stats free, since checkout is US dollars) sell the same purchase through their stats page: `components/exam/ExamStatsPage.tsx` shows 5 rows (2 on phones) and locks the rest like the DMV `/stats`, checkout location `<examId>_stats` (the family id for a state version), which `purchaseExam()` in `lib/purchaseAttribution.ts` credits to that exam. The purchase email (`purchaseWelcome`) leads a stats buyer back to that exam's stats (`EmailVoice.statsPath`, `/<exam>/stats` for v2 too) and otherwise the DMV unlock, and lists "full stats on every other US exam"; nothing anywhere sells SAT or ACT access. A browser in a teacher's class for the exam (`isClassStudent()` in `lib/classProgress.ts`, quiz memberships excluded) sees every stat free, on the DMV `/stats` too.

**Common Mistakes** (the most-missed questions, "we know which questions everyone fails") is built nightly by `/api/cron/aggregate-stats` from every real account's training answers and finished practice tests: `globalStats/wrongQuestions` for the DMV (universal questions) and `globalStats/examWrongQuestions` for every v1 registry exam (matched by `questionIdPrefix`, a state version under its own id), plus an `available` list. A test only gets it once 20 questions each have 10 answers (`lib/communityStats.ts`); from that night on, with no code change, it shows (no header icon since #589; the header carries only Your Stats) a Common Mistakes card on the exam dashboard, a "Short on time?" block on the landing (rendered by `ExamRelatedTests`; the DMV landing's is wrapped in `CommunityGate`) and a Common Mistakes tab on the stats page (`?tab=community`, open to guests, locked past 5 rows like Your Stats). Clients read `/api/community-stats/exams` once per page load (`useCommunityAvailable()`), CDN-cached for an hour. v2 exams get it the same way: the cron reads `users/{uid}.v2` through `v2QuestionPerformance()` (held-out tests skipped so Common Mistakes never shows them), keyed by the v2 exam id, shown as a tab on `StatsV2` and a card on `DashboardV2`.
- To add a v2 exam: an `ExamV2Config` in `lib/v2/exams/` (with `landingPath`), register it, a bank module `lib/v2/banks/<exam>.ts` that imports the JSON and calls `registerBank()` (each exam page imports it for that side effect, and the shared test, results and practice routes load it on demand, so a page bundles only its own bank; name it by the exam id), run `tools/validate_v2_bank.py` so `lib/v2/bankSizes.ts` carries its question count (the catalog reads that, never a bank), `app/<slug>/` wrappers copied from `app/sat/` (layout, redirect, dashboard, stats; never test or practice folders, which are the shared `app/[slug]` routes), a landing copied from `app/sat-practice-test/`, a catalog entry, a `[data-theme]` block, a sitemap line, and an import of its bank in `lib/server/classQuestions.ts` so the class page can show its questions.

### SEO conventions

- **Landing pages** (`app/<x>-practice-test/page.tsx`) are the only exam URLs meant to rank. Each sets its own metadata (title, description, canonical, Open Graph image at `/og/<examId>` from `app/og/[examId]/route.tsx`) and a `WebApplication` + `FAQPage` JSON-LD graph (no breadcrumb: removed Oct 2026, the crumb pushed the headline down and Google no longer shows trails on mobile), and renders `<ExamRelatedTests examId>` before the final CTA (cross-links within the exam's hub group from `relatedTests()` in `lib/testCatalog.ts`). Write metadata and JSON-LD strings with plain apostrophes; `&apos;` only belongs in JSX text.
- **App routes** (`app/<slug>/layout.tsx`) export `examAppMetadata(id)` from `lib/examSeo.ts`: the exam's own title and `noindex, follow`. They are deliberately not disallowed in `app/robots.ts` so crawlers can read the tag. DMV app routes keep their robots.txt disallow.
- **GEO (AI answer engines)**: every exam landing renders `<ExamFacts examId>` under the hero: a plain answer about the real exam, a facts table and a dated "based on" line with the official source, plus a `WebPage` node with `dateModified` (`EXAM_LANDINGS_UPDATED_AT`). The facts live in `lib/examFacts.ts`; keep them in step with the landing's FAQ and add an entry with each new exam. `/llms.txt` and `/llms-full.txt` are generated from the catalog, exam facts and state data (`lib/llmsTxt.ts`, DMV first, with the 51-state written-test table). The site-wide `Organization` and `WebSite` nodes are in `lib/siteSchema.ts`, rendered once by `app/layout.tsx`; point new JSON-LD at them by `@id`. `app/robots.ts` gives every crawler, AI or not, the same allow/disallow lists. First visits are counted by source (`visitSource()` in `lib/funnel.ts`: ChatGPT, Perplexity, Gemini, Copilot, Claude, search, direct, other), shown on the Growth tab. DMV state pages are deliberately left as they are.
- **Sample questions** (`components/exam/ExamSampleQuestions.tsx`): the 29 non-US driving test landings show six bank questions (the last of each category in ID order, sign-image and "A and B" items skipped, options rotated so keys spread over A to D) with answers and explanations in plain HTML plus a `Quiz` JSON-LD node, for "<test> questions and answers" searches and AI answers. The page imports its own bank (`import "@/lib/banks/<id>"`), so nothing else bundles it; add both lines to a new country's landing. `ExamRelatedTests` links a country's exam up to its country homepage, and country homepages list each local test's `EXAM_FACTS` answer under "About each test". `/llms.txt` has a generated "Practice tests by country" section (`countrySection()` in `lib/llmsTxt.ts`).
- **IndexNow** (`/api/indexnow/ping`, nightly cron) submits every sitemap URL to Bing, which ChatGPT search reads. The key file is served at the host root, `/<key>.txt` (a rewrite in `next.config.ts` to `/api/indexnow/key`), because a key file's folder limits which URLs it may submit.
- **Footer** links stay inside the current test's cluster (`relatedTests`): DMV pages link to CDL, endorsements and motorcycle plus the `/tests` hub, never all thirty exams.
- **Sitemap** is an index (`app/sitemap.xml/route.ts`) over per-family files in `app/sitemaps/[segment]/route.ts` (`dmv`, `dmv-es-vi-ko` (which also holds the Chinese pages; the name is kept so Search Console keeps its history), `exams`; `/teach` is in `exams`) built by `lib/sitemaps.ts`, so Search Console shows DMV coverage separately. `lastmod` comes from the hand-bumped dates in `lib/seoDates.ts`; bump the relevant constant when a page family's content changes.

These pages are the DMV flow, not the CDL one: `lib/examRoutes.ts` (`DMV_ROUTES` / `getExamRoutes(id)`) parameterises the shared pieces (`hooks/useTestResults.ts`, `components/results/*`, `components/MissDrill.tsx`, `components/dashboard/ProgressCard.tsx`, `lib/missedQuestions.ts`, `components/AttemptChart.tsx`) by route base, test IDs, pass line, and premium gating. Defaults reproduce DMV behaviour exactly; when changing the DMV results/drill/dashboard flow, keep every exam working.

Theme colors come from the `[data-theme="<examId>"]` blocks in `app/globals.css`; `contexts/TestThemeContext.tsx` and `components/HeaderSwitch.tsx` pick the header by path. Every header logo is `components/BrandLockup.tsx`, the same everywhere: the DMV tiger (`/tiger.png`, or the crowned `/tiger_face_01.png` for a Premium account via `useIsPremium()`) and "Tigertest", never a test's own tiger or name. It goes home: the **current test**'s dashboard, else `/`. The current test is the last dashboard opened (DMV with or without a state, any registry exam, any v2 exam), stored as `primaryExam` + `primaryExamAt` in `useStore`, written to `users/{uid}` on its own by `setPrimaryExam` (the newer visit wins on sign-in, cleared on logout) and read through `useCurrentTest()` / `useHomePath()` in `hooks/useHomePath.ts`. Landing pages, tests and results never change it; the All tests menu pins it as Current, neutral pages (`/tests`, `/settings`, `/admin`) wear its header, and the emails talk about it. `tools/build_logo_svgs.py` still writes the older per-test lockups as standalone SVGs to `public/logos/<id>.svg` and `<id>-dark.svg` (DMV states under `public/logos/dmv/`) for off-site use.

### Languages

Two separate languages. The **interface language** is the person's own (`useStore.language`, synced to `users/{uid}.language` with `languageChosen`, mirrored to the `tt-lang` cookie in `lib/language.ts`): every page follows it, picked in the footer or on `/settings`; until someone picks, their country's language applies (`REGIONS[].lang`). Only landings whose URL is in a language keep that language (`lib/pageLanguage.ts`). The **test language** is what a test's questions are in: only the languages that exam really exists in (`examLanguages()`, `dmvLanguagesFor(state)` for the DMV), chosen with `TestLanguageChoice` on its dashboard and kept per exam in `useStore.testLanguages` (key `dmv` or the exam id); with no pick it follows the interface language when the exam has it, else the exam's own (`hooks/useTestLanguage.ts`). Never machine-translate a question bank just to offer a language. Homepage bodies still render in their country's language (`homeCopy` has en and de only).

### Dark mode

Class strategy (`darkMode: ["class"]`): `contexts/ThemeContext.tsx` keeps the preference (`light` / `dark` / `system`) in localStorage under `tigertest-theme` (a device setting, never synced to the account), toggles `dark` on `<html>` and follows the OS while on `system`. `THEME_INIT_SCRIPT` runs inline in `app/layout.tsx` `<head>` so a dark reader never sees a white flash; `<html>` carries `suppressHydrationWarning` for that reason. `components/ThemeToggle.tsx` is the picker in the footer (never the header), and `ThemeSegmentedControl` the one on `/settings`; labels are under `theme.*` in `i18n/*`.

Components keep their light classes and carry a `dark:` companion, one palette throughout: page `bg-gray-50` becomes `dark:bg-gray-950`, cards `bg-white` become `dark:bg-gray-900`, insets `bg-gray-100` become `dark:bg-gray-800`, borders `gray-200` become `dark:gray-800`, body text `gray-900` becomes `dark:gray-50`, secondary `gray-600` becomes `dark:gray-300`; tinted boxes go to the deep end of their hue (`bg-green-50 dark:bg-green-950`, `text-green-700 dark:text-green-300`); black CTA buttons (`bg-black text-white`) invert to white; translucent whites and blacks, solid brand and semantic fills, and `text-gray-400` stay as they are; hero gradients end on `dark:to-transparent`. The shadcn tokens in the `.dark` block of `globals.css` use the same grays. `tools/add_dark_variants.py` applies those rules mechanically and is idempotent, so run it after adding a page or component that uses hardcoded palette classes (or write the `dark:` companion by hand). Per-theme brand tints for dark (`.dark [data-theme=...]`, brand-light, gradient-to, border-light darken; brand-dark and brand-darker lighten; brands under 50% lightness lift to 50%) are generated by `tools/gen_dark_brand_css.py`; re-run it when adding a theme block. v2 exams get the same tints at runtime from `lib/v2/darkTheme.ts` through `V2Shell`, and `components/v2/v2.css` carries the `.dark .v2-shell` / `.dark .v2-focus` overrides. v2 figures are grayscale SVGs and are shown with `dark:invert`.

### Email

Resend, from `noreply@tigertest.io`, reply-to John. Templates are HTML strings in `lib/email-templates.ts`, one function of an `EmailVoice` (`lib/email-voice.ts`) each. Daily campaign crons under `app/api/cron/*` (schedules in `vercel.json`) share `lib/cron-email.ts`: one Auth list call, `getEligibleUsers()` (consent, opt-out, quiet-days rule per exam), a 24h frequency cap, a once-only `emailsSent` key per campaign, and the account-wide daily budget in `lib/email-quota.ts` (bump `CAMPAIGN_CRON_COUNT` when adding a cron). `scripts/email-dryrun.mjs` shows who each cron would reach without sending.

Opt-out is `users/{uid}.unsubscribed` (`lib/unsubscribe.ts`). It is checked in the audience query and again in `sendCronEmail()` right before every send, and every campaign carries RFC 8058 `List-Unsubscribe` headers pointing at `/api/unsubscribe` (GET and one-click POST). Nothing on the client writes that field. The new-tests campaign (`newTests2026`) is paused unless `NEW_TESTS_CAMPAIGN=send`; while paused each daily run only logs how many people it would reach. DMV readers are split across the variants still sending in `lib/email-launch.ts` (v4 and v5; v1 and v3 retired Oct 17 via `RETIRED_VARIANTS`) (one per user, stable by uid, stamped as `emailVariants.newTests2026` on send; links go through `/api/email/click`, which records `emailClicks.newTests2026`). The split-test card on the Growth tab was removed Oct 30; the stamps are still written. Non-DMV readers get the short version, outside the test. It also asks "what should we build next?": clicks land in the `testRequests` collection via `/api/feedback/test-request` and `/request-test` (`lib/test-requests.ts`), shown on the Growth tab; a named exam emails John immediately.

### Mobile Apps

`/mobile/` contains a Capacitor 8 shell (app id `io.tigertest.app`) that loads

the shell via a `TigerTestApp` user-agent token (`lib/native-app.ts`,

### Agentic Question Rewrite System

`/agentic-rewrite/` contains a multi-agent pipeline for generating and validating questions. A supervisor agent orchestrates generators and four validator agents (distribution, memorization, format, answer-length) with a fixer agent for corrections. State question files live in `/agentic-rewrite/states/`.

```
NEXT_PUBLIC_SITE_URL            # Site URL for metadata
ANTHROPIC_API_KEY               # Claude API, for the daily update on the /admin Today tab (cron skips when unset)
CRON_SECRET                     # Bearer token for /api/cron/* and /api/indexnow/ping
INDEXNOW_KEY                    # 8–128 char hex key for IndexNow (Bing) submissions
EMAIL_REPLY_TO                  # Reply-To on campaign mail and test-request notifications (default john@johnbrophy.net)
CRON_MAX_BATCH                  # Per-run campaign cap (default: daily campaign budget / cron count)
NEW_TESTS_CAMPAIGN              # "send" turns on the SAT/ACT launch email; anything else (or unset) = paused, logs a daily dry-run count
NEW_TESTS_WINNER                # Optional launch-email variant id (v4 or v5, a retired id is ignored): sends everyone not yet emailed that variant
QUIZZES_CAMPAIGN                # "send" turns on the quizzes launch email (/api/cron/quizzes-launch); anything else (or unset) = paused, logs a daily eligible count
MCP_TOKEN_SECRET                # HS256 signing key for the MCP server's access tokens (rotating it logs every client out)
MCP_OAUTH_ISSUER_URL            # Public URL of the MCP server / site (https://tigertest.io): JWT issuer and the base of the links tools return
```

**MCP study continuation**: `list_in_progress_tests` discovers only the caller’s synced account progress (site started-test signals, plus learned Basics/custom quiz history). `get_study_progress`, `start_study_practice`, and `submit_study_answer` add v1 registry and v2 drill practice without replacing legacy DMV or custom-quiz tools. Catalog practice updates `users/{uid}.trainingSets`/history; v2 uses its existing drills and grader. Pending attempt IDs prevent stale answer replay. Timed/adaptive sittings remain web-only and unchanged. Browser sync is not live collaboration. MCP writes increment per-store mcpProgressRevisions (catalog/v2/quiz); browser save transactions reject stale revisions and latch a visible conflict until explicit reload. This preserves newer cloud progress without guessing reset/delete merge intent; unsynced browser work may need repeating. Scope baselines are captured before local replacement, never refreshed mid-session. No model calls.
