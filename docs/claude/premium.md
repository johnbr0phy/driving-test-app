# Premium, locks, prices, guest checkout, Common Mistakes

Moved verbatim from CLAUDE.md on 2026-11-20. Keep it current when the code changes.

- **Premium** is the one DMV purchase (`$9.99` one-time in the US, a local price elsewhere, `users/{uid}.subscription.isPremium`), which also unlocks any v2 exam whose config has `premium`. Since Nov 10 2026 that is the 54 career, licensing, government-job and graduate-admission exams in `PREMIUM_V2_IDS` (`lib/v2/registry.ts`), which sets it for them: the last quarter of the drills and practice tests is Premium (the last test when there are two, the rest from the last drills; a one-test exam locks only drills), the v1 rule carried over. School, college-entrance and children's tests (SAT, PSAT, ACT, AP, GED, GCSE, KS2, 11+, NAPLAN, selective tests, JNVST, AISSEE, JAMB, JEE, NEET, CUET, MHT-CET, NDA, ACCUPLACER, Högskoleprovet and the rest) are never sold: a new v2 exam is free unless its id is added to that list, and John has said not to sell the kids' or GCSE tests. A student in a teacher's class for the exam is never locked (`hooks/useV2Premium.ts`), and work already started stays open. Logic is in `lib/v2/premium.ts`; `useIsPremium()` reads the flag once auth settles. `V2TestGate` fronts every v2 test route (an in-progress or already-sat test stays open), `DrillRunner` shows a lock screen for a locked drill (open anyway if the person already has their own progress in it), and `DashboardV2` locks those steps and the test step and verifies the Stripe return (`usePurchaseReturn`; checkout takes a same-site `returnPath`). v2 paywall item ids start `v2_`, which tells the paywall follow-up email (`lib/paywallAbandon.ts`) the hit was on that v2 exam. Client-side gating, like the DMV. Every v1 registry exam, in every country (since Nov 2026, priced locally through `lib/pricing.ts`), sells the same purchase through their stats page: `components/exam/ExamStatsPage.tsx` shows 5 rows (2 on phones) and locks the rest like the DMV `/stats`, checkout location `<examId>_stats` (the family id for a state version), which `purchaseExam()` in `lib/purchaseAttribution.ts` credits to that exam. The purchase email (`purchaseWelcome`) leads a stats buyer back to that exam's stats (`EmailVoice.statsPath`, `/<exam>/stats` for v2 too) and otherwise the DMV unlock, and lists "full stats on every other exam on Tigertest, in every country"; nothing anywhere sells SAT or ACT access. A browser in a teacher's class for the exam (`isClassStudent()` in `lib/classProgress.ts`, quiz memberships excluded) sees every stat free, on the DMV `/stats` too.

**Full-length mocks (v1, Nov 15 2026).** An exam can add timed full-length mocks after its practice tests (`ExamConfig.mockExams`: count, minutes, its own blueprint): store IDs `idBase + testCount + 1...`, so `examTestIds()`, `getExamForTestId()` and everything keyed by test ID include them (`examTestTotal()`, `isMockTest()`, `examTestLength()`); questions are an even spread over each category's whole pool (`mockQuestions()` in `lib/examTestGenerator.ts`, no question in two mocks, reusing practice-test questions: a dress rehearsal, not new content). `ExamTestPage` opens a mock on a start screen and runs a clock from the session's saved `startedAt`, so a reload keeps it, and scores at zero with unanswered questions wrong; the dashboard and results read each test's own length. Strings in `ExamUiMock` (`lib/examUi.ts`, en and es; other languages read English). Only RBT uses mocks so far. There is no readiness verdict on any stats page (an "Are you ready?" card shipped and was removed the same day, Nov 15 2026: Tigertest cannot promise a pass estimate is right). Premium copy (`premiumBenefits`, paywalls, landings) says plainly what it adds, more questions, more tests, timed mocks, full stats, and never promises a pass or readiness; `tests/exam-locks.test.cjs` checks the bullets.

**v1 exam locks (Nov 10 2026, "start for free"; a quarter of the dashboard since Nov 14 2026).** On every v1 registry exam the last 25% of the dashboard steps are Premium (`lib/examLocks.ts`: `lockedStepCount()` is 25% of training steps plus tests, rounded, at least one; `examSteps()` is the dashboard order and the locked steps are its tail, read through `lockedTrainingParts()` and `lockedTestIds()`), so a longer exam locks more. An 8-step exam (Motorcycle) locks steps 7 and 8, EPA 608 steps 5 and 9, Life in the UK its last set and Tests 7 and 8, CDL (13 training steps, 6 tests) its last three training steps and Tests 5 and 6; a state version (one test) locks only its last one or two training steps, so its one test stays free. v2 Premium exams follow the same count over drills plus tests (`lib/v2/registry.ts`: the last test when there are two, the rest from the last drills, so an 8-drill exam locks two drills and Practice Test 2). The DMV keeps its own rule (sets and tests 3 and 4). `hooks/useExamLocks.ts` decides per person: open for Premium, for a student in a teacher's class for the exam, and for any step the person already has work in (a started or finished test, a mastered or queued question in that part), and only once the account has loaded (`settled`), so pages that gate entry wait for it. `ExamDashboard` shows the lock on the card and opens the paywall (`useExamPaywall` in `components/exam/ExamLockScreen.tsx`, checkout location `<familyId>_dashboard`, `_test` or `_set`, item ids prefixed `exam_` so the paywall follow-up email knows the exam, purchase verified on the dashboard by `usePurchaseReturn`); `ExamTestPage` and `ExamTrainingPage` show `ExamLockScreen` for a locked URL (its three strings are in `lib/examUi.ts` for all seventeen languages). Client-side gating like the DMV; the MCP study tools are not gated. Super Amazing Mode on a v1 exam therefore needs Premium. Catalog entries carry `pricing` ("3 free, 1 premium"), so cards read "Free + Premium" and `ExamFacts` says "free to start". Copy rule: say "Start for free" / "free to start", never that everything or every set and test is free, on v1 exams or the paid v2 exams in any language; only the free v2 exams (school and children's tests) may say everything is free. Page titles keep "Free ... Practice Test". The hero subtitle of every landing for an exam with Premium steps ends "Free to start, no account needed." (its own form in other languages; Nov 14 2026, so the "Free" headline is never read as "all of it is free"), pinned by `tests/landing-free-to-start.test.cjs`. The homepage tagline is "Any test, anywhere. Start free." `tests/exam-locks.test.cjs` pins the rule.

**Lock share test (Nov 21 2026).** Half of browsers see the last 50% of every v1 registry exam dashboard locked instead of 25%, to learn whether locking more sells more Premium per visitor (`lib/lockTestIds.ts`, test `lockShare1`, arms `25` and `50`; browser side `lib/lockTest.ts`, localStorage `tigertest-lock-test`, `?locks=25|50` pins it). `lockedStepCount()`, `lockedTestIds()` and `lockedTrainingParts()` take an optional share (default `LOCKED_SHARE`); `hooks/useExamLocks.ts` passes this browser's share once settled, and whatever the share, Test 1 and at least one training step stay free (an 8-step exam at 50% locks Sets 3 and 4 and Tests 3 and 4, the DMV's shape). The 50% arm always covers the 25% locks. A settled visit by someone not Premium and not in a class counts once per exam per page load in `analytics/lockTest` (views and distinct browsers per arm, `/api/analytics/lock-test`, internal, test, declined and bot browsers skipped) and stamps `users/{uid}.lockTest`; every checkout sends `lockArm`, which rides the Stripe metadata onto the `payments` doc. `LockTestCard` on the A/B tests tab shows buyers and revenue per 100 browsers per arm with a p-value. Server-side text (catalog `pricing`, the purchase email's list of what Premium opens) keeps the 25% rule; the landing Try one now card picks only from sets free in both arms (`LOCK_MAX_SHARE`). The DMV and v2 exams are not in the test. `tests/exam-locks.test.cjs` pins it. To end it, keep the winning share as `LOCKED_SHARE`, drop the share argument from `useExamLocks` and update the copy rules here and in CLAUDE.md.

**Local prices** (`lib/pricing.ts`): Premium is shown and charged in the visitor's currency, both from Vercel's `x-vercel-ip-country` (`lib/server/visitorCountry.ts`): `/api/price` feeds `usePremiumPrice()` (`hooks/usePremiumPrice.ts`, cached per tab by `lib/localPrice.ts`) on every paywall and lock, and `/api/stripe/checkout` charges the same price with inline `price_data` (dollars keep `STRIPE_SINGLE_PRICE_ID`). Hand-set prices per currency, about $10 in richer countries and about $5 where that is a lot (INR, PHP, MYR, ZAR, NGN, KES, PKR and others); a country not in the table, or a currency the US Stripe account refuses (GHS), pays dollars. Off production `?country=XX` on any page tries another currency (kept in the `tt-price-country` cookie so checkout follows). The webhook stores `currency`, `country` and `amountUsdCents` (Stripe's settled dollars) on each `payments` doc, and /admin revenue reads `paymentNetUsdCents()` so every figure stays in US cents. GA4 purchase events carry the local value and currency.

**Guest checkout** (Nov 19 2026): Premium can be bought without an account. Every buy button calls `startCheckout()` (`lib/startCheckout.ts`; it waits for `auth.authStateReady()`), which sends the ID token when signed in and nothing when not. For a guest, `/api/stripe/checkout` (at most `GUEST_CHECKOUTS_PER_IP_PER_DAY`, 30, per IP in `guestCheckoutLimits`) makes a session with `metadata.guest = "1"`, no customer and `customer_creation: "always"`, so Stripe asks for the email, and gives the browser a random key in an httpOnly cookie named per session (`guestKeyCookie()`, path `/api/stripe`) whose sha256 is `metadata.guestKey`. A return path may carry a simple query (`?tab=community`). `resolveGuestBuyer()` (`lib/server/guestCheckout.ts`) turns the email into an account (the existing one, or a new unverified Firebase user whose uid is `guestUidFor(session.id)`, so "made by this checkout" is exactly `uid === guestUidFor(session.id)` and no other session can claim it) and pins it in `guestCheckouts/{sessionId}`, so the webhook, `/api/stripe/verify-purchase` and the success page agree. `/api/stripe/guest-session` hands a custom token only for an account this checkout made, to the browser holding that checkout's key, within 24 hours, while the account has no password or Google on it (repeatable, so a failed sign-in can be retried); a leaked success URL gets `other_browser`. `components/GuestPurchaseReturn.tsx` (root layout, in Suspense) signs them in, moves their guest progress over without the conflict dialog (`lib/guestPurchaseSignIn.ts`, tied to the uid; marketing consent starts off, since they never saw the box), confirms Premium once the account has loaded, and shows a message for every other outcome (existing account, already Premium and refunded, sign in with Forgot password, still paying, another browser, error with retry). `checkUserHasData` ignores Premium only on a `gc_` account; `convertGuestToUser` reads the account's `subscription`; purchase checks (`usePurchaseReturn`, the DMV dashboard) wait for `loadedUid === uid` so the account load cannot undo them. Because anyone can pay with an address that has no account and be signed in to it, the first sign-in to a `gc_` account with the email verified (Google for that address, or a password set through the reset email) calls `/api/account/guest-claim`, which unlinks every other sign-in method, revokes every refresh token and hands the caller a fresh token (`guestCheckoutClaims/{uid}`, once). A guest who pays for an account that already has Premium is refunded by the webhook (`duplicateGuestPurchase`, idempotency key `guest-duplicate-<session>`; `charge_already_refunded` counts as done, a refund Stripe refuses for good is written to `guestCheckoutProblems` for a person). The receipt (`purchaseWelcomeHtml()`) tells a guest which account Premium went to and how to sign in elsewhere; for an account the checkout made, its button is a one-tap sign-in link (`guestSignInLink()`, `/login/link#s=<session>&t=<token>`, one per session in `guestLoginLinks/{sessionId}`, reusable for 7 days, token in the fragment so it never reaches a server log or analytics). `/api/account/guest-link` checks it, marks the email verified (opening it proves the inbox), on first use does the guest-claim takeover (unlink every other sign-in, revoke sessions) and returns a custom token, and stands in for the signup welcome (the webhook adds `welcome` to `emailsSent`); the `payments` doc records `guestCheckout` (`new_account` / `existing_account`). Paywalls show guests the buy button with a small Create account link; the native app keeps sign-up first. `tests/guest-checkout-flow.test.cjs` runs the routes against fake Stripe and Firebase.

**Common Mistakes** (the most-missed questions, "we know which questions everyone fails") is built nightly by `/api/cron/aggregate-stats` from every real account's training answers and finished practice tests: `globalStats/wrongQuestions` for the DMV (universal questions) and `globalStats/examWrongQuestions` for every v1 registry exam (matched by `questionIdPrefix`, a state version under its own id), plus an `available` list. A test only gets it once 20 questions each have 10 answers (`lib/communityStats.ts`); from that night on, with no code change, it shows (no header icon since #589; the header carries only Your Stats) a Common Mistakes card on the exam dashboard, a "Short on time?" block on the landing (rendered by `ExamRelatedTests`; the DMV landing's is wrapped in `CommunityGate`) and a Common Mistakes tab on the stats page (`?tab=community`, open to guests, locked past 5 rows like Your Stats). Clients read `/api/community-stats/exams` once per page load (`useCommunityAvailable()`), CDN-cached for an hour. v2 exams get it the same way: the cron reads `users/{uid}.v2` through `v2QuestionPerformance()` (held-out tests skipped so Common Mistakes never shows them), keyed by the v2 exam id, shown as a tab on `StatsV2` and a card on `DashboardV2`. The cron reads accounts in 8 parallel parts (Nov 2026: one function took 250 to 280 s for 5,300 accounts and timed out some nights): GET lists accounts once, POSTs each uid slice to the same route at `SITE_URL` with `CRON_SECRET` (`lib/server/aggregateStats.ts` scans and merges; every sum is per account, so parts add up exactly), then writes the docs. Without a secret, or if the parts fail within 30 s, it scans in one call as before.
