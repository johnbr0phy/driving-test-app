# v1 registry exams: engine, state variants, translated and native-language exams

Moved verbatim from CLAUDE.md on 2026-11-20. Keep it current when the code changes.

Non-DMV exams reuse the DMV components and store, namespaced by ID range and a
pseudo state code so progress never collides with DMV data. All of them are driven by the registry in `lib/exams.ts` (`ExamConfig`: state code, ID bases, slug, landing path, blueprint, training sets, category labels, dashboard copy). Each exam's bank is its own module, `lib/banks/<examId>.ts` (English plus any translated banks), registered into `lib/examData.ts` by `registerExamBanks()` and imported for that side effect only by the exam's stats and drill pages and loaded on demand by the shared test and practice pages, so a page bundles its own exam's questions and no other's (and never the DMV banks: answer shuffling lives in `lib/shuffleOptions.ts`); `lib/banks/all.ts` loads every bank for scripts only; `lib/examTestGenerator.ts` builds blueprint-weighted deterministic tests (test N takes slice N of each category pool, sorted by question ID) and training sets (one or more categories per set, or a test's own questions; see DMV-style test sets below). No training session runs much past 50 questions: a set over 60 (`TRAINING_PART_MAX`) shows on the dashboard as parts of about 50, each its own step (`?set=N&part=P`; without `part` the page opens the first unfinished one). A part is a contiguous run of the set in question-ID order, and its start IDs and sizes are generated into `lib/trainingParts.json` by `npx tsx scripts/build-training-parts.ts` (the dashboard does not bundle banks); progress stays stored per set id and parts only filter it, so server progress, admin and emails are unchanged and existing mastery fills part 1 first. The script cuts where the category changes whenever sizes allow (a single-category set is cut evenly), and every split set carries hand-written `partNames` (what each part actually covers, e.g. CDL "Night Driving", "Weather Driving", "Mountains & Railroad Crossings"; Spanish ones in the CDL translation), shown on the dashboard, the training page and its "Next:" button; without them a part falls back to "<set>, part 2 of 3", and the script warns when the count does not match. Re-read the stems and rename when a split changes. Re-run the script (`--check` reports staleness and any set `size` that does not match its bank) after changing a bank or a set's categories. Pages under `app/<slug>/` are thin wrappers around `components/exam/*` (dashboard, drill, stats) plus a static SEO landing; the test, results and practice pages of every v1 and v2 exam are one shared set of routes, `app/[slug]/test/[id]`, `app/[slug]/test/[id]/results` and `app/[slug]/practice/[n]` (`components/exam/SharedExamAppPage.tsx`, layout `SharedExamAppLayout.tsx`), which find the exam by its `slug` (`examForAppSlug()` in `lib/examAppRoute.ts`) and import its bank on demand (`loadExamBank()`, one chunk per bank, so a bank file must be named by the exam id). They replaced about 650 per-exam copies that broke production deploys on Vercel's 2,048-route limit in Nov 2026: never add `test/[id]`, `test/[id]/results` or `practice/[n]` under a new exam's folder (a per-exam folder would win over the shared route and add about ten routes back). What counts toward the limit (measured with a real `vercel build`, Nov 14 2026: 303 of 2,048): a static page costs nothing, so an exam's dashboard, stats, drill and landing pages are free; a dynamic route costs about 3, and each middleware matcher, redirect, rewrite and header rule 1. `tests/route-budget.test.cjs` fails at an estimated 1,200. The build itself is the nearer limit: it ran out of memory at Node's default heap locally and wrote 5 GB of `.next`. State variants keep their own `[state]` routes (`app/<slug>/page.tsx`, or `landingPath` when it lives elsewhere). `lib/testCatalog.ts` lists every test (DMV + registry) for the `/tests` hub, header switcher and footer.
**Training sets are named by topic (Nov 2026).** Every registry exam's training sets are content-area sets with a topic name ("Safety & Compliance", never "Training Set 1"): one or more categories per set, 35 to 60 questions where the pools allow (a bigger single topic splits into parts with hand-written `partNames`), usually four sets, in the official outline's order with a small set last (the last training step is Premium), names of about 35 characters or fewer in the outline's own words, and `weightLabel` "13 of 50 test questions". From Oct 22 to Nov 11 2026, 84 exams instead trained DMV-style, set N holding exactly practice test N's questions (`testSets()` in `lib/exams.ts`, `test` on the set def, named "Training Set N"); John chose topic names over that pairing, accepting that an early test now includes topics not trained yet. The machinery (`testSets`, `hasTestSets`, `TEST_SET_NAMES`) is still there but no exam uses it: do not use it for a new exam. Those 84 kept their set IDs, so `lib/testSetMigration.ts` (`BACK_TO_TOPIC_SETS`, the list of them) regroups stored progress by question on the dashboard and training page through `useTestSetMigration`, loading the exam's bank on demand, and drops set IDs the exam no longer has; it is a no-op once regrouped. Translated exams carry set names in `translations[lang].trainingSets`. Every registry dashboard still alternates training and tests (since Nov 2026, so people test themselves early): `ExamDashboard` spreads the tests evenly through the training steps, test i after step ceil((i+1)*P/T), so a test always comes last (CDL: two or three sets, then a test); only the on-screen order changes, progress is stored by set and test ID, and the section headings (`copy.trainingHeading` / `testsHeading`) are no longer shown.

**State variants** (real estate CA, NJ, TX, FL, NY, PA, IL, OH, GA, NC, MI, VA, WA, AZ, TN and LA; life & health and P&C insurance TX, FL, CA, NY, PA, IL, OH, GA, NC, MI, NJ, VA and WA) are full `ExamConfig`s with `variantOf` and `jurisdiction`, listed in `EXAM_VARIANTS` (not `EXAMS`, so the catalog, sitemap, emails and theme see one family). Each has its own ID range (CA test 3901 and sets 3901-3904, NJ 3951 and 3951-3954, TX 4001, FL 4051, NY 4101, each with sets +1 to +4), pseudo state code (`REALESTATE_CA`) and question prefix (`RECA-`), so progress and mastery never mix across states and no migration is needed. Store lookups (`getExamById`, `getExamForTestId`, `getExamByStateCode`...) search `ALL_EXAMS`; `getExamByPath` returns the family. Pages live at `app/real-estate/[state]/*` via `useExamVariant()` (unknown or uppercase codes 404). `components/exam/ExamStatePicker.tsx` uses the DMV onboarding sentence, but its dropdown lists only the family's variant states plus "Other state" (stored as `OTHER`) so it never implies coverage we lack: `ExamStatePrompt` is a card on the family dashboard only until a state is chosen, then `ExamStateLine` is one line in the hero with a Change control. Since Nov 15 2026 a family dashboard with no state sets the visitor's IP state (`/api/geo`, `useSuggestedState`) when that state has a variant, as if they had chosen it (GA4 `state_selected` with `via: "geo"` and `exam`), and forwards to it; the prompt shows only when there is no such guess, never auto-picking "Other state". The choice is the real state code in `examStates[familyId]` (synced to `users/{uid}.examStates`, never touches the DMV `selectedState`); "Other state" (and any older saved non-variant code, which reads as Other) stays on the national bank, labeled national-only. Opening a state dashboard records it, and the family dashboard forwards to a remembered state that has a variant. Banks come from the reviewed handoff forms via `tools/build_re_state_banks.py` (one full-length test per state: CA 150, NJ 110, each item the form's state-resolved question, `sourceQuestionId` kept). TX (120: 80 national, 40 Texas, Pearson VUE scored counts since Jan 2026), FL (100, 75% pass, DBPR outline) and NY (75, weighted to the DOS 77-hour course; DOS publishes no count or pass mark) come from `tools/build_state_variant.py realestate <ST> <dir>` instead: national items picked for the state (conflicting ones excluded, some reworded for state law, keys never changed) plus state-law items `RE<ST>-<ST><SEG>-NNN`; it prints the category counts that are the config's blueprint. Each state's official sources and national picks/exclusions are in `docs/re-state-sources/`. Insurance variants are built the same way (`tools/build_state_variant.py insurance|pnc <ST> <dir>`, ids `LH<ST>-`/`PC<ST>-`, state codes `LIFEHEALTH_TX`, `PNC_CA`...): L&H TX 130 (100 general + 30 Texas, Pearson VUE), FL 150 (the 2-15 exam), CA 150 (CDI's combined life and A&H exam, 60% pass); P&C TX 130, FL 150 (2-20, capped from 160), CA 150 (combined, 60%). ID blocks L&H 4150/4200/4250, P&C 4300/4350/4400; routes `app/life-health-insurance/[state]/*` and `app/property-casualty-insurance/[state]/*`; sources in `docs/insurance-state-sources/`. The second batch (real estate PA to TN, insurance NY to WA, Oct 2026) is built the same way, each `national.json` carrying its `"total"`; ID blocks of 50 from 4450 (real estate PA, IL, OH, GA, NC, MI, VA, WA, AZ, TN), 4950 (L&H NY, PA, IL, OH, GA, NC, MI, NJ, VA, WA) and 5450 (P&C, same order). States whose exam is one integrated form (MI, OH, PA, NY, VA, WA, GA insurance) place state items where the outline cites state law; states that test each line separately (NC, NJ, IL insurance) get both lines on one form, capped at 150 keeping the general to state ratio; where the parts pass at different marks (VA, IL real estate) `passPct` is the stricter one. State banks register the same way, through `registerExamBanks()` in `lib/banks/{realEstate,lifeHealth,propertyCasualty}States.ts`, which only the `[state]` pages (and `lib/banks/all.ts`) import, so other exams never bundle them. Louisiana (Nov 2026, Pearson VUE, 80 national + 55 state items, ID block 5950 after the P&C blocks) leaves out the common-law national items that do not fit its civil law (joint tenancy, life estates, deeds of trust, warranty deed types, adverse possession, equitable title) and adds Civil Code items (component parts, usufruct, servitudes, community property, acquisitive prescription, authentic act, lesion, redhibition, earnest money, reconduction, forced heirs). To add a state: build its bank, add a variant config and an entry in its family module, then re-run `scripts/build-training-parts.ts`; to add a family, add `[state]` wrappers under its slug.

**State practice tests.** Each of the 46 real estate and insurance state versions offers three short practice tests, followed by the original full-length exam. Every short test mixes the general questions selected for that state with its state-law questions. The three tests together cover the state's reviewed form exactly once. The full-length exam revisits that material. A short test gets 25 to 50 questions according to the bank size. The dashboard has eight steps, or nine when a large training topic already has two parts. The national "Other state" option uses its own four 50-question tests. The original full-length exam keeps URL number 1 and its store ID. Short tests use URL numbers 2 to 4, in dashboard order before the full-length exam. Use `examTestLength` for each score denominator and `examDashboardTestIds` for presentation order.

Short state forms deal questions evenly by topic and by origin (shared or state-specific). The optional `statePracticeSeed` fixes the order within those groups using the question IDs. Keep a published seed stable when editing wording. Run `node --test tests/state-practice-forms.test.cjs` on changes. It checks each full and short form against the same answer-length and stem-echo limits as the bank tools. Fix wording cues across the full bank first. When preparing a new form, check the seed against the actual distribution in each short test.

**Translated exams.** An exam is offered in another language by a translated bank registered from the exam's `lib/banks/<examId>.ts` (`TRANSLATED_BANKS` in `lib/examData.ts`, same questionIds, categories and answer keys, so tests, sets and progress are identical across languages) plus `ExamConfig.translations[lang]` (name, labels, set names, category labels, dashboard copy). The shared exam pages read everything through `useLocalizedExam()` (`hooks/useLocalizedExam.ts`): `examLanguage()` picks the person's global `language` when the exam has it and English otherwise, `localizeExam()` merges the copy, and `lib/examUi.ts` holds the page strings that are not in `i18n/*` (add a language there too). The footer switcher shows on the exam's app pages, limited to `examLanguages(exam)`. A test keeps the language it was started in (questions are stored on the session); training and stats follow the switch at once. Fix an answer key in both banks. Translated so far: CDL (es, hand-written landing `app/es/examen-practica-cdl`), Food Handler (es, vi, ko), CDL Endorsements, OSHA 10, Forklift, CNA and EPA 608 (es, landing `/es/examen-epa-608`; temperatures written `°F`), Spain DGT (es-ES, landing `/es/test-dgt-permiso-b`), Portugal IMT (pt-PT, landing `/pt/testes-codigo-imt`), Greece (el-GR, landing `/el/test-kok-diploma-odigisis`), the Sweden theory test (sv-SE, landing `/sv/teoriprov-korkort-b`), the Denmark theory test (da-DK, landing `/da/teoriproeve-bil`), the Finland theory test (fi-FI, landing `/fi/ajokortin-teoriakoe`), the Hungary KRESZ test (hu-HU, landing `/hu/kresz-teszt`), the Romania DRPCIV test (ro-RO, landing `/ro/chestionare-drpciv-categoria-b`), the Belgium theory test in Dutch and French (nl-BE, landing `/nl/theorie-examen-rijbewijs-b-oefenen`; fr-BE, landing `/fr/examen-theorique-permis-b`), the Netherlands CBR car theory test (nl-NL, landing `/nl/cbr-theorie-examen-auto-oefenen`, x-default) and, the other way round, the German theory test in English (en-DE, landing `/en/fuehrerschein-theorie-test`). All non-CDL translations are machine translations awaiting native review. Every exam but CDL keeps its translated copy in `lib/examTranslations/<exam>.<lang>.json` (loaded through `examTranslation()`, which checks the five hero subtitles) and its landing content in `lib/landings/<exam>.<lang>.json`, rendered by `components/exam/TranslatedExamLanding.tsx` from a three-line page at the translation's `landingPath` (`/es/examen-cna`, `/vi/thi-thu-the-food-handler`, `/ko/food-handler-siheom`...). English landings list every language through `examLandingAlternates()` (`lib/examSeo.ts`). `lib/examUi.ts` and `ExamLandingHero` carry en, es, vi and ko; the exam category labels in `i18n/{es,vi,ko}.ts` are translated for the translated exams (results pages read them). Landing screenshots are `public/landing/<examId>-{mobile,desktop}-<lang>.png`. Validate a new translated bank against its English one (same ids and keys, every text field translated, "both/all/none" options still caught by the shuffle guard) before wiring it.

**Native-language exams** (Nov 2026, phase 0 of `tools/next100/LANGUAGES.md`). An exam whose own language is not English is a normal registry exam with `ExamConfig.language` (base bank and copy in that language), `locale` ("de-DE"), `english` (the names every English surface uses: catalog, `/tests`, All tests menu, llms.txt, admin) and `review` per language (`machine`, `model`, `native`); `translations` may now hold any language, so a German exam's English version is `translations.en` on the same id. `examLanguages()` puts the base first, `examLanguage()` falls back to the base (an English-UI person opening the German exam gets German questions), and `localizeExam()` leaves the base unchanged. The UI runs in seventeen languages (en, es, vi, ko, zh, de, fr, it, pl, nl, pt, sv, da, fi, hu, ro, el): `i18n/{de,fr,it,pl,nl,pt,sv,da,fi,hu,ro,el}.ts` are machine-translated pending native review (the six Nordic, Hungarian, Romanian and Greek ones added Nov 2026, with no region switched to them yet), carry no category names (`createT` falls back to English for any missing key) and leave DMV-only blocks English. `contexts/LanguageContext.tsx` keeps the stored choice as `preferredLanguage` and exposes the page's `language` from `lib/pageLanguage.ts`: a native exam's pages run in its language, DMV pages (`isDmvPath`) only in `DMV_LANGUAGES` (en, es, vi, ko, zh; anything else reads English, since the DMV has no German questions), a country homepage in its region's `lang`; it sets `html lang`. The footer switcher offers `DMV_LANGUAGES` on DMV pages. Results and the DMV stats page read the exam's own `categoryLabels` before `i18n` categories. Per-language tables: `TEST_SET_NAMES` and `trainingPartName` (`lib/exams.ts`), `EXAM_UI` (`lib/examUi.ts`, zh included), `COPY` (`ExamLandingHero`), `SAMPLE_COPY` and `RELATED_COPY` (`ExamSampleQuestions` and `ExamRelatedTests` take `lang`), `CARD_FOOTERS` (`lib/shareCards.ts`, exam cards in the exam's language, never ko or zh), the shuffle guard's per-language list (`lib/shuffleOptions.ts`). `TranslatedExamLanding` renders a native exam's base landing too (`lang` = base, URL = `landingPath`), takes `samples` and `related`, uses `examLandingLocale()` for og:locale and inLanguage, `facts.source` from the landing JSON, and EUR (or the country's currency) on EU exams; an unwired exam's landing is a 404, not a failed build. `examLandingAlternates()` keys hreflang by locale ("es-ES"; US translations keep "es") with x-default on the translation written for the exam's own country. Regions carry `lang` and `locale` (`REGION_HREFLANG` derives from them): every region is English except Germany (`de`, `app/de/layout.tsx`), Spain (`es`), Portugal (`pt`), Sweden (`sv`, `app/se/layout.tsx`; the `/sv` landings get `app/sv/layout.tsx`), Denmark (`da`, `app/dk/layout.tsx`; the `/da` landings get `app/da/layout.tsx`), Greece (`el`, `app/gr/layout.tsx`; the `/el` landings get `app/el/layout.tsx`), Finland (`fi`, `app/fi/layout.tsx`, which also wraps the `/fi` landings), Hungary (`hu`, `app/hu/layout.tsx`, which also wraps the `/hu` landings), Romania (`ro`, `app/ro/layout.tsx`, which also wraps the `/ro` landings), France (`fr`, `app/fr/layout.tsx`, which also wraps the `/fr` landings) and Belgium (`nl`, though its test is in English). `components/home/homeCopy.ts` holds the homepage, catalog card and country pill strings per language (en and de), `lib/landingContent.ts` the landing JSONs a non-English homepage quotes under "About each test", and a homepage hides its country CTA and local section until that test is in the catalog. `CountryPills` shows the current country, the visitor's own, the last picked and the five largest (`LARGEST`), with "More countries" opening a plain-link list of the rest. Tooling: `validate_bank.py --lang xx` (language's banned phrases and connectors, `--len-scale`, default per language), `validate_translation.py <base> <xx> --lang xx`, and the "Native-language exam" section of `.claude/skills/exam-bank/references/wiring.md`.

To add an exam: add an `ExamConfig` to `lib/exams.ts`, a bank module `lib/banks/<examId>.ts` (named by the exam id, and a line in `lib/banks/all.ts`) imported at the top of `app/<slug>/{stats,drill}/page.tsx` (the shared test and practice routes load it themselves), a `[data-theme]` block in `app/globals.css`, the category keys to `types/index.ts` and `i18n/*.ts`, and the `app/<slug>/` wrappers (layout, redirect, dashboard, drill, stats; no test or practice folders) and landing. Every blueprint count times `testCount` must fit inside that category's pool. Training sets are topic sets with topic names (see "Training sets are named by topic"); every category belongs to exactly one set and each set's `size` is its pool size. Then run `npx tsx scripts/build-training-parts.ts`. The `exam-bank` skill (`.claude/skills/exam-bank/references/wiring.md`) is the full checklist; keep it in step when the wiring changes, since every new exam is built from it. Wrappers stay thin: a change one exam needs goes in the shared `components/exam/*` piece or an `ExamConfig` field, so every exam, new or old, keeps the same dashboard, results and landing.
